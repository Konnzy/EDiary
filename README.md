# EDiary - електронний щоденник навчального закладу

Клієнт-серверний вебзастосунок для ведення журналу, розкладу, домашніх завдань,
успішності та комунікації між адміністрацією, вчителями, учнями й батьками.

## Структура

```text
EDiary/
|-- frontend/   # React 19.2, Vite 8.3, Tailwind CSS 4.3, ECMAScript 2025
|-- backend/    # Java 25, Spring Boot 4.1.1, Hibernate 7.4.10.Final, PostgreSQL 18.3
`-- README.md
```

## Вимоги

- Java 25;
- Maven 3.9+ або Maven Wrapper;
- PostgreSQL 18.3;
- Node.js 24 LTS та npm 11+;
- SMTP-сервер для надсилання результатів розгляду заявок.

## Docker Compose

Docker Compose запускає лише backend і frontend. PostgreSQL залишається на
хостовому комп'ютері та не створюється, не зупиняється і не видаляється разом
із Docker-контейнерами. Перед запуском переконайтеся, що локальний PostgreSQL
працює, а база `ediary` уже містить потрібну схему й дані.

Скопіюйте `.env.example` у `.env` у корені проєкту та за потреби вкажіть назву
БД, порт, користувача й пароль, які використовує ваш локальний PostgreSQL.
Файл `.env` ігнорується Git, тому секрети не потраплять до коміту.

Запустіть frontend і backend через Docker Desktop або з PowerShell у корені:

```powershell
Copy-Item .env.example .env
# Відредагуйте .env і вкажіть фактичні реквізити вашої локальної БД.
docker compose up -d --build
docker compose ps
```

Docker Desktop покаже лише `ediary-backend` і `ediary-frontend`. Контейнер
backend підключається до PostgreSQL на цьому ж комп'ютері через
`host.docker.internal` (Docker Desktop hostname для доступу контейнера до хоста).
Браузер відкриває frontend за `http://127.0.0.1:5173`; Nginx у frontend-
контейнері пересилає запити `/api` до backend. Порт `8081` також доступний
локально для перевірки API.

Окремо можна запускати `docker compose up -d backend` або
`docker compose up -d frontend`. Зупинка через `docker compose down` прибирає
лише ці два контейнери; локальний PostgreSQL і його дані не зачіпаються.

Якщо змінився код і потрібно перебудувати відповідний образ, додай `--build`,
наприклад `docker compose up -d --build backend`.

Compose читає налаштування підключення з `.env`: `EDIARY_DB_HOST`,
`EDIARY_DB_PORT`, `EDIARY_DB_NAME`, `EDIARY_DB_USERNAME` та
`EDIARY_DB_PASSWORD`. Значення за замовчуванням відповідають локальним
налаштуванням backend (`ediary`, порт `5432`, користувач/пароль `ediary`), але
їх потрібно звірити з налаштуваннями сервера у pgAdmin.

Якщо PostgreSQL відхиляє з'єднання з контейнера, перевірте, чи сервер слухає
TCP-з'єднання, чи `pg_hba.conf` дозволяє підключення з Docker Desktop, та чи
брандмауер Windows не блокує його. Не відкривайте PostgreSQL для публічних
мереж. Backend, запущений безпосередньо з IDE, як і раніше використовує
`localhost:5432` і налаштування в `backend/src/main/resources/application.yaml`.

Якщо потрібно явно перевизначити локальні IDE-налаштування:

```powershell
$env:EDIARY_DB_URL = "jdbc:postgresql://localhost:5432/ediary"
$env:EDIARY_DB_USERNAME = "ediary"
$env:EDIARY_DB_PASSWORD = "ediary"
```

Flyway автоматично виконує міграції з `backend/src/main/resources/db/migration`.
Hibernate працює в режимі `validate` і не змінює схему самостійно.

Якщо міграція `V1__init_schema.sql` уже застосовувалась до постійної БД, її не
можна редагувати повторно. Наступні зміни схеми потрібно оформлювати як `V2`,
`V3` тощо.

## Перший адміністратор

Початковий адміністратор створюється лише за явного ввімкнення bootstrap. Пароль
повинен містити щонайменше 12 символів, великі й малі літери, цифру та спеціальний
символ. Код доступу складається із шести літер або цифр; дефіс необов'язковий.

```powershell
$env:EDIARY_BOOTSTRAP_ADMIN_ENABLED = "true"
$env:EDIARY_BOOTSTRAP_ADMIN_LOGIN = "admin"
$env:EDIARY_BOOTSTRAP_ADMIN_EMAIL = "admin@school.edu.ua"
$env:EDIARY_BOOTSTRAP_ADMIN_PASSWORD = "replace-with-a-strong-password"
$env:EDIARY_BOOTSTRAP_ADMIN_ACCESS_CODE = "ABC-123"
$env:EDIARY_BOOTSTRAP_ADMIN_FIRST_NAME = "Ім'я"
$env:EDIARY_BOOTSTRAP_ADMIN_LAST_NAME = "Прізвище"
```

Після першого успішного запуску встановіть
`EDIARY_BOOTSTRAP_ADMIN_ENABLED=false` і видаліть секрети bootstrap із середовища.
У БД пароль і службовий код зберігаються тільки як BCrypt-хеші.

## Демонстраційні дані

Після виконання Flyway-міграції локальну БД можна наповнити одним класом,
адміністратором, учителем і учнем:

```powershell
cd backend
psql -h localhost -U ediary -d ediary -f src/main/resources/db/seed/dev/seed_demo_data.sql
```

Скрипт можна запускати повторно: наявні записи не дублюються. Тестові дані:

| Роль | Логін | Пароль | Код адміністратора |
| --- | --- | --- | --- |
| Адміністратор | `admin.test` | `AdminPass!234` | `ABC-123` |
| Вчитель | `teacher.test` | `AdminPass!234` | - |
| Учень | `student.test` | `AdminPass!234` | - |

Dataset призначений виключно для локальної розробки й не повинен виконуватися
в production.

## Пошта

```powershell
$env:EDIARY_MAIL_ENABLED = "true"
$env:EDIARY_MAIL_HOST = "smtp.example.com"
$env:EDIARY_MAIL_PORT = "587"
$env:EDIARY_MAIL_USERNAME = "smtp-user"
$env:EDIARY_MAIL_PASSWORD = "smtp-password"
$env:EDIARY_MAIL_AUTH = "true"
$env:EDIARY_MAIL_STARTTLS = "true"
$env:EDIARY_MAIL_STARTTLS_REQUIRED = "true"
$env:EDIARY_MAIL_SSL = "false"
$env:EDIARY_MAIL_TEST_CONNECTION = "true"
$env:EDIARY_MAIL_FROM = "no-reply@example.com"
$env:EDIARY_MAIL_FROM_NAME = "Електронний щоденник"
```

Значення потрібно додати до Environment variables конфігурації запуску в
IntelliJ і перезапустити backend. `EDIARY_MAIL_TEST_CONNECTION=true` змушує
застосунок перевірити SMTP під час старту: з неправильними реквізитами backend
не запуститься, а причина буде одразу видима в консолі. Для локального SMTP без
автентифікації використовуйте порт `1025`, `EDIARY_MAIL_AUTH=false` і
`EDIARY_MAIL_TEST_CONNECTION=false`.

## Запуск

Backend:

```powershell
cd backend
.\mvnw.cmd spring-boot:run
```

Frontend:

```powershell
cd frontend
npm install
npm run dev
```

Frontend використовує `http://127.0.0.1:8081/api`. Для іншої адреси задайте
`VITE_API_URL` перед запуском або production-збіркою.

## Реєстраційний модуль

- `POST /api/registration-requests` - подання публічної заявки;
- `GET /api/registration-requests/options` - класи та предмети для форми;
- `GET /api/admin/registration-requests` - захищений список заявок;
- `POST /api/admin/registration-requests/{id}/approve` - схвалення і створення акаунта; приймає `{ "login": "student.petrenko" }`, а для зайнятого логіна повертає `409 LOGIN_ALREADY_EXISTS`;
- `POST /api/admin/registration-requests/{id}/reject` - відхилення з причиною.

Адміністративні операції захищені роллю `ADMIN`, серверною сесією та CSRF.
Для production потрібно завершувати TLS на reverse proxy та встановити
`EDIARY_SECURE_COOKIE=true`.

## Перевірка сесії та захист маршрутів

`GET /api/auth/session` повертає поточного активного користувача і його роль за
серверною `HttpSession`. Frontend перевіряє цей endpoint перед відображенням
кабінетів адміністратора, учня, вчителя та батьків. Адміністративні маршрути
додатково вимагають роль `ADMIN`; без відповідної сесії користувач повертається
на екран входу адміністратора.

## Відновлення пароля

`POST /api/auth/password/forgot` приймає `{ "email": "user@example.com" }`.
Відповідь однакова для відомої та невідомої адреси. Надсилання працює через
наявні `EDIARY_MAIL_*` налаштування SMTP у фоновій черзі.

`POST /api/auth/password/reset` приймає `{ "token": "...", "newPassword": "..." }`.
Обидва запити потребують CSRF-токена з `/api/security/csrf`.
Посилання одноразове, діє 30 хвилин; у `password_reset_token` зберігається SHA-256 хеш.
Після зміни пароля відкликаються інші токени та сесії користувача.

Задайте `EDIARY_FRONTEND_URL` як адресу frontend без hash-маршруту
(локальне значення: `http://127.0.0.1:5174`). Для відкриття листа з іншого
пристрою потрібна доступна з цього пристрою адреса, у production — HTTPS.
Зміна змінних середовища потребує перезапуску backend.

Повторний лист для акаунта дозволено через 2 хвилини. На одну IP-адресу
діє ліміт 5 запитів листа та 20 спроб скидання за 15 хвилин.
IP-ліміти й фонова черга локальні для одного процесу; для кількох інстансів
потрібне спільне сховище лімітів і надійна черга доставки.

## Управління користувачами

- `GET /api/admin/users` - список користувачів із пошуком, фільтрами та пагінацією;
- `POST /api/admin/users` - створення учня, вчителя або батьків адміністратором;
- `PATCH /api/admin/users/{id}/status` - блокування або розблокування;
- `GET /api/admin/users/{id}/deletion-eligibility` - перевірка можливості видалення;
- `DELETE /api/admin/users/{id}` - фізичне видалення акаунта без важливої історії.

Під час створення генерується криптографічно випадковий тимчасовий пароль,
який зберігається лише як BCrypt-хеш. Після commit транзакції логін і тимчасовий
пароль надсилаються користувачу через налаштований SMTP. Створення іншого
адміністратора в цьому endpoint заборонено.

Акаунти з оцінками, відвідуванням, домашніми завданнями, класом, предметами,
розкладом, повідомленнями або зв'язками батьків видалити не можна. Для них
використовується блокування: дані зберігаються, а вхід до системи
забороняється. Реєстраційна заявка, технічні сесії, reset-токени й
налаштування сповіщень не вважаються навчальною історією та видаляються разом
із дозволеним акаунтом.

## Управління класами

- `GET /api/admin/classes?academicYear=2026/2027` - класи обраного навчального року з пошуком і фільтром за паралеллю;
- `GET /api/admin/classes/options` - активні вчителі та їхні призначення;
- `GET /api/admin/classes/{id}` - деталі класу;
- `GET /api/admin/classes/{id}/deletion-eligibility` - перевірка можливості видалення класу;
- `GET /api/admin/classes/{id}/students` - фактичний склад класу;
- `GET /api/admin/classes/students/unassigned?academicYear=2026/2027` - активні учні без класу в обраному році;
- `POST /api/admin/classes` - створення класу;
- `PATCH /api/admin/classes/{id}` - редагування класу;
- `POST /api/admin/classes/{id}/students/{studentId}` - додавання учня;
- `PATCH /api/admin/classes/{id}/students/{studentId}/class` - переведення учня;
- `DELETE /api/admin/classes/{id}/students/{studentId}` - вилучення учня зі складу класу без видалення акаунта.
- `DELETE /api/admin/classes/{id}` - видалення щойно створеного класу без пов'язаних даних.

Номер класу обмежений діапазоном від 1 до 12, літера має бути однією великою
українською літерою. Поєднання номера та літери унікальне в межах навчального
року. Один учитель може бути класним керівником лише одного класу в межах року.
Кожен клас належить конкретному року; склад учнів зберігається окремими
історичними записами. Архівні роки доступні лише для перегляду. Місткість є сталою для всіх класів
і дорівнює 30 учням; змінити її через API або адміністративний інтерфейс не можна.
Учень може тимчасово не належати до класу, при цьому його акаунт та навчальна
історія зберігаються. Клас можна видалити лише за відсутності класного
керівника, учнів, розкладу та реєстраційних заявок, що посилаються на нього.

## Управління предметами

- `GET /api/admin/subjects` - список предметів із пошуком за назвою;
- `GET /api/admin/subjects/options` - список учителів для призначення;
- `POST /api/admin/subjects` - створення предмета та призначення вчителів;
- `PATCH /api/admin/subjects/{id}` - редагування назви та складу вчителів;
- `GET /api/admin/subjects/{id}/deletion-eligibility` - перевірка можливості видалення;
- `DELETE /api/admin/subjects/{id}` - видалення предмета без пов'язаних даних.

Один предмет можуть викладати декілька вчителів, а один учитель може бути
призначений до декількох предметів. Назва предмета унікальна без урахування
регістру. Не можна зняти призначення вчителя, якщо відповідна пара
«вчитель-предмет» використовується в розкладі. Видалення дозволене лише за
відсутності призначених учителів, розкладу та реєстраційних заявок.

## Schedule Module

Адміністратор створює та редагує двотижневий розклад через
`/api/admin/schedules`. Розклад зберігається окремо для класу, навчального року
та номера тижня. Час восьми уроків є сталим, а перед збереженням сервер
перевіряє місткість слота, призначення вчителя до предмета та конфлікти
вчителя між класами.

Якщо для слота вже існує проведений `Lesson`, редагування або видалення слота
архівує попередній запис розкладу. `Lesson` і пов'язані з ним оцінки,
відвідування та домашні завдання зберігають посилання на історичний запис;
новий розклад читає лише активні записи. Міграція `V13` також забороняє
змінювати або видаляти такі історичні записи безпосередньо в БД.

- `GET /api/schedules/options` - доступні навчальні роки та поточний тиждень;
- `GET /api/student/schedule` - розклад класу автентифікованого учня;
- `GET /api/teacher/schedule` - лише уроки автентифікованого вчителя;
- `GET /api/parent/children/{studentId}/schedule` - розклад власної прив'язаної дитини.

Користувацькі запити приймають лише `week` зі значенням `1` або `2`.
Навчальний рік автоматично визначається сервером за поточною датою і не може
бути підмінений користувачем. Сервер також визначає профіль учня чи вчителя з
поточної сесії. Для батьків додатково перевіряється зв'язок із запитаною
дитиною, тому підміна `studentId` не надає доступу до чужого розкладу.
Frontend-маршрути `/student/schedule`, `/teacher/schedule` і
`/parent/schedule` захищені відповідними ролями та відображають дані з БД.

Новий навчальний рік адміністратор може створити лише після його фактичного
початку. До 1 вересня спроба створити майбутній період повертає
`409 ACADEMIC_YEAR_NOT_STARTED`.

## Панель адміністратора

`GET /api/admin/dashboard` повертає фактичні кількості користувачів за ролями
і статусами, кількість заявок на розгляді, останні реєстраційні заявки та
заняття поточного дня. Дані dashboard формуються безпосередньо з PostgreSQL;
демонстраційні лічильники та події на головній сторінці не використовуються.

## Навчальні дані та сповіщення

### Системи оцінювання

У вкладці адміністратора «Предмети» форми створення та редагування задають
єдині правила предмета для всіх класів і навчальних років. Типово використовується
бальна система 1–12. У заліковому режимі звичайні уроки містять відвідування,
тему та ДЗ без числових оцінок; для тематичних, семестрових і річних робіт
учитель обирає «зар.» або «не зар.». Порожній результат не є незарахуванням.

Незалежні дозволи «зар.» у бальній системі та «зв.» додають відповідні
підсумкові результати. Перевірка документальних підстав відбувається поза
застосунком. Результат не визначається автоматично за відвідуванням.
Нечислові результати не включаються до середнього бала; у заліковому режимі
середній бал і прогнози не розраховуються. Змінювати систему після внесення
результатів або вимикати дозвіл, який уже використано, сервер не дозволяє.

Міграція V31 додає `mark_result`, а V32 переносить правила на рівень предмета
в `subject_assessment_policy`, не змінюючи наявні результати. Стару таблицю
`assessment_policy` залишено лише як історичний знімок; застосунок її не читає
і не редагує. Якщо старі налаштування відрізнялися між класами, дозволи
об'єднуються, а наявні числові оцінки зберігають бальний режим. Якщо для одного
предмета вже існують одночасно бали й «не зар.», міграція зупиняється без
перетворення даних: потрібне явне узгодження системи оцінювання.
Нове введення «З» як відвідування вимкнено; історичні записи
`EXEMPTED` збережені та доступні для перегляду. Заміна їх на «П»/«Н»
автоматично не виконується. Зміни правил і результатів фіксуються в аудиті.

API адміністратора: `GET /api/admin/subjects`, `POST /api/admin/subjects` та
`PATCH /api/admin/subjects/{subjectId}`. Поле `assessmentPolicy` містить
`mode` (`NUMERIC`/`PASS_FAIL`), `allowPassed`, `allowExempted`. Відповідь також
містить `hasResults` для блокування зміни системи після внесення результатів.
У запиті редагування без `assessmentPolicy` чинні правила зберігаються.
Запит клітинки журналу містить або `score`, або `result`
(`PASSED`/`NOT_PASSED`/`EXEMPTED`), але не обидва значення.

Списки оцінок, відвідування й домашніх завдань показують по 20 записів на
сторінку для учня, батьків, класного керівника та адміністратора. Пагінація
виконується на frontend після фільтрації й сортування повного списку;
статистика та середній бал рахуються за весь обраний період. Для періоду
«Увесь навчальний рік» показується середній бал, а не орієнтовна тематична.

Сповіщення в застосунку завжди ввімкнені. У профілі налаштовуються лише
поштові сповіщення, які за замовчуванням вимкнені. Міграція V27 зберігає
наявний вибір поштових сповіщень; історичні налаштування каналу в застосунку
більше не впливають на доставку. Видалені користувачем і відкликані сповіщення
не відновлюються. Службові листи про доступ і відновлення пароля не залежать
від цих налаштувань.

## Повідомлення та поштові сповіщення

Міграція V30 додає персональне приховування подій заявок для адміністраторів.
Для учня, батьків і вчителя `DELETE /api/notifications` приховує всі поточні
сповіщення тільки цього користувача. Черга пошти, приватні повідомлення й
навчальні записи не видаляються. Прев'ю сповіщення має два окремі рядки:
предмет із дедлайном/оцінкою та зміст події; коротке ім'я дитини додається
тільки батькам. У всіх ролей кнопка має назву «Очистити сповіщення».
`DELETE /api/admin/registration-requests/notifications/{id}` приховує подію
опрацьованої заявки; `DELETE /api/admin/registration-requests/notifications`
очищає історію опрацьованих заявок цього адміністратора. Заявки на розгляді
залишаються видимими, а самі заявки, рішення та аудит не видаляються.

Міграція V29 зберігає повний текст поштового повідомлення окремо від короткого
сповіщення в застосунку. Листи містять головні деталі та підписане посилання на
відповідний розділ. Для доступу з інших пристроїв задайте `EDIARY_FRONTEND_URL`
як доступну адресу frontend: `127.0.0.1` підходить лише для цього комп'ютера.

Для розкладу зберігається знімок «Було / Стало» до зміни сутностей: день,
номер і час уроку, предмет, учитель, кабінет, дата дії. У лист потрапляють лише
змінені поля; загальна дата події та незмінені дані не повторюються. Додавання та скасування
позначаються явно; перенесення між різними слотами відображається як скасування
старого та додавання нового уроку. Учитель отримує зміни своїх занять, класний
керівник — зміни класу. Оцінки розрізняють нове значення та виправлення зі старим
і новим балом із 12; ДЗ — створення та редагування, з коротким описом і дедлайном.
Нагадування про дедлайн містить саме завдання; відвідування — заняття й чітке
скасування попередньої відсутності. Приватний лист у поштовому сповіщенні
представлений відправником і темою, без копіювання повного тексту.

Міграція V28 додає ідемпотентні запити надсилання повідомлень та загальний тип
поштової доставки `NOTICE`. API `/api/messages` доступний учню, батькам і вчителю:

- `GET /api/messages?folder=inbox|sent|important&page=0` — сторінки по 20 листів і кількість непрочитаних;
- `GET /api/messages/recipients?query=...` — пошук дозволених одержувачів за ПІБ, до 20 результатів;
- `GET /api/messages/recipients?id=...` — перевірка одержувача з переходу з іншої сторінки;
- `POST /api/messages` — `{ recipientId, subject, text, clientRequestId }`, де останнє поле є UUID;
- `POST /api/messages/{id}/open` — відкриття; прочитання позначається лише для одержувача;
- `PUT /api/messages/{id}/important` — `{ important: true|false }`, лише для одержувача.

Одержувачі визначаються сервером за чинним навчальним роком: учень і батьки
пишуть учителям своєї дитини/класу, вчитель — пов'язаним учням та їхнім батькам.
Класний керівник має доступ до свого класу навіть без уроків у розкладі.
У списку одержувачів учня та батьків класні керівники пов'язаних дітей мають
пріоритет перед іншими вчителями й окремий підпис. Пріоритет застосовується
до обмеження у 20 результатів, але не скасовує пошук за введеним ПІБ.
Учасники зберігають доступ до старих листів після зміни навчальних призначень.
Чужі листи недоступні за підміною ID. Важливими позначаються отримані листи;
відправник не змінює цей вибір одержувача. Повторний запит з тим самим UUID
не створює другого листа; змінений вміст потребує нового UUID.

Події оцінок, ДЗ, дедлайнів, розкладу, класних подій і повідомлень створюють
запис черги в тій самій транзакції, що й сповіщення. Відправлення працює після
commit, повторно перевіряє поштові налаштування й активність акаунта та має
до 5 спроб із наростаючою затримкою. Вимкнений SMTP не витрачає спроби.
Відсутність і її виправлення зберігають окрему перевірку актуального статусу
та хвилинну затримку початкового листа. Нові категорії не ставлять у чергу
історичні сповіщення. SMTP не дає гарантії exactly-once при збої між прийняттям
листа поштовим сервером та commit у БД.
